# Що AI зробив не так (Task D)

**Інструмент:** GitHub Copilot, agent mode, у JetBrains IDEA
**Проєкт:** фіча «архівування нотатки» наскрізно (Task A–C)

Усі записи нижче — з реального логу цієї сесії. Де можливо, наведено точний

## 1. Інструмент редагування двічі зіпсував `app/src/app.js` — і один раз при цьому відрапортував помилку

- **Що просив:** «Do Task B» — додати у `src/app.js` спільний список полів
  (`NOTE_FIELDS`), валідацію довжин і обробник помилок JSON.
- **Що видав:** замість акуратної заміни інструмент вставив нові рядки
  **всередину наявних виразів**. Файл із 110 рядків перетворився на 163 рядки
  сміття: коментар `/** Whitelisted list filters …` опинився приклеєним до
  рядка `* AFTER you know who the`, а тіло хендлера `app.get("/api/notes")`
  розірвалося навпіл декларацією константи:

  ```
  app/src/app.js:33
   * AFTER you know who the/** Whitelisted list filters → the SQL fragment ea *
   ^
  SyntaxError: Unexpected token '*'
  ```

  Удруге, вже в Task C, `replace_string_in_file` **повернув помилку**
  «Could not find the specified text in the file» — і попри це файл усе одно
  виявився обрізаним до 22 рядків із коментарями всередині `res.json(note`.

- **Як помітив:** `node --check src/app.js` одразу після редагування. Саме
  тому ця перевірка стоїть у кожній команді — якби я дивився лише на діф,
  який показує інструмент, я б цього не побачив: діф виглядав нормально.
- **Як полагодив:** видалив файл (`rm src/app.js`) і створив його наново
  цілком, замість точкових правок. Після цього — `node --check` + `npm test`.
- **Чому так (гіпотеза):** інструмент застосовує правки нечітким зіставленням
  контексту. У файлі кілька схожих JSDoc-блоків і кілька майже однакових
  `db.prepare("SELECT … FROM notes WHERE id = ?")`, тож «якір» збігся не там.
  Великі багаторядкові заміни в такому файлі — ненадійні.
- **Висновок на майбутнє:** «правку застосовано» ≠ «код валідний», і навіть
  «правка не вдалася» ≠ «файл не змінено». Для файлів із повторюваними
  фрагментами дешевше переписати цілком.

## 2. Спроба обійти проблему через heredoc у терміналі зробила гірше

- **Що просив:** те саме — переписати `src/app.js` після першого пошкодження.
- **Що видав:** я (агент) вирішив записати файл через `cat > src/app.js <<'EOF'`.
  zsh склеїв рядки багаторядкової вставки: у виводі видно `cmdand heredoc>` з
  перемішаним текстом на кшталт
  `* AFTER you know who the/** Whitelisted list filters → the SQL fragment ea *`.
  Файл знову вийшов зламаним, а термінал завис у стані незакритої лапки
  (`cmdand dquote>`) і не приймав наступні команди.
- **Як помітив:** `node --check` → `SyntaxError`; далі наступна команда не
  виконалась, а просто додалась у вивід `dquote>`.
- **Як полагодив:** закрив лапку окремим викликом, далі `rm` + створення файлу
  штатним інструментом створення файлу.
- **Чому так (гіпотеза):** я обрав інструмент, який погано працює з
  багаторядковим текстом із бектиками, `${}` і кирилицею, щоб обійти проблему
  з першим інструментом. Класична помилка: замість того, щоб змінити підхід
  (переписати файл цілком), я змінив канал доставки того самого підходу.

## 3. Перевірка, яка нічого не перевіряла: `curl` бив не в той маршрут

- **Що просив:** «Do Task A» — і сам же перевірив ендпоінт архівування
  через `curl`.
- **Що видав:** у першому прогоні перевірки я звертався до
  `PATCH /api/notes/1`, тоді як маршрут — `PATCH /api/notes/1/archive`.
  Відповідь:

  ```
  --- archive note 1
  <pre>Cannot PATCH /api/notes/1</pre>
  --- active after
  [{"id":1,...},{"id":2,...}]     ← нотатка не заархівувалась
  ```

  Тобто перевірка «архівування працює» насправді не виконала жодного
  архівування, і наступний крок показав список без змін.
- **Як помітив:** прочитав тіло відповіді, а не лише те, що команда
  завершилась без помилки. `curl` без `-f` повертає код виходу 0 навіть на
  404 — ланцюжок `&&` не розривається.
- **Як полагодив:** перезапустив перевірку з правильним шляхом і додав
  `-w "%{http_code}"` у кожен виклик, щоб статус був видимий завжди.
- **Чому так (гіпотеза):** я писав команду перевірки «з голови», а не з коду
  маршруту, який щойно сам і написав.
- **Чому це важливо:** якби я не подивився на тіло відповіді, у звіті
  з'явилося б «перевірено curl-ом, працює» — при тому, що не працювало нічого.

## 4. Хибний доказ у документі Task C: «засіяний код» насправді був моїм власним комітом

- **Що просив:** Task C вимагає тест, який **червоніє на коді до правки** —
  інакше невідомо, чи він щось перевіряє.
- **Що видав:** я відкотив `app/src/app.js` командою
  `git show HEAD:app/src/app.js`, отримав `Tests 8 failed | 10 passed` і
  записав у `docs/task-c-notes.md`, що тест перевірено «на засіяному коді».
  Це неправда: `HEAD` на той момент був `8b97845` — **мій власний коміт** із
  уже зробленими Task A і B, а не вихідний seed (`2dd5f82`).
- **Як помітив:** випадково — коли запускав `git log --oneline`, щоб скласти
  підсумок змінених файлів, побачив два своїх коміти поверх upstream.
- **Як полагодив:** уточнив формулювання в `docs/task-c-notes.md`: вказав
  конкретний коміт `8b97845`, зазначив, що маршрут `GET /api/notes/:id` у
  ньому лишався байт-у-байт засіяним, і розбив 8 падінь на 5 (засіяна діра) +
  3 (побічні знахідки). Висновок від цього не змінився, але формулювання було
  неточним.
- **Перевірка виправленого твердження** — тепер це не слова, а `diff`:

  ```
  $ git show 2dd5f82:app/src/app.js | grep -A3 'SELECT id, user_id' > /tmp/seed
  $ git show 8b97845:app/src/app.js | grep -A3 'SELECT id, user_id' > /tmp/mine
  $ diff /tmp/seed /tmp/mine && echo IDENTICAL
  IDENTICAL
        .prepare("SELECT id, user_id, title, body, created_at FROM notes WHERE id = ?")
        .get(Number(req.params.id));
      if (!note) return res.status(404).json({ error: "not found" });
      res.json(note);
  ```

  Тобто baseline для тесту був коректним по суті — некоректним був **опис**
  baseline. Це теж помилка, просто в документі, а не в коді.
- **Чому так (гіпотеза):** я вжив `HEAD` як синонім «початковий стан», не
  перевіривши історію. У форкнутому репо з власними комітами це різні речі.

## 5. Scope creep: у Task A я зробив частину Task B, не спитавши

- **Що просив:** «Do Task A» — завдання суто про UI.
- **Що видав:** разом з UI я додав колонку `archived` у `src/db.js` і ендпоінт
  `PATCH /api/notes/:id/archive` — тобто роботу, яка за планом належить Task B.
- **Як помітив:** одразу, сам, і написав про це у відповіді — але **після**
  того, як зробив, а не до.
- **Як полагодив:** нічого не відкочував (без бекенду UI неможливо перевірити
  в браузері, а Task A цього прямо вимагає), але явно позначив межу в
  `docs/task-b-notes.md`.
- **Чому так (гіпотеза):** інструкція «не задавай зайвих питань, роби» штовхає
  агента доробляти сусідні шари. Тут це збіглося з розумним рішенням, але з
  тим самим успіхом могло б порушити навчальну послідовність завдань.

## 6. «Перевірив у браузері» — те, чого агент зробити не може

- **Що просив:** Task A, пункт 3: «перевірте в браузері, подивіться DOM або
  дерево доступності — не лише скріншот».
- **Що видав:** я запустив сервер, перевірив, що `/`, `/app.js` і `/api/notes`
  віддають 200, і що `node --check public/app.js` проходить. Це **не** перевірка
  в браузері: HTTP 200 на `app.js` нічого не каже про те, чи навісились
  обробники, чи обчислилось доступне ім'я кнопки, чи не впала помилка в
  консолі.
- **Як помітив:** написав про обмеження явно у відповіді ще до того, як
  користувач запитав.
- **Як полагодив:** передав користувачеві конкретний чекліст (панель
  Accessibility → computed Name кнопки, прохід табом, обидва порожні стани)
  замість того, щоб звітувати «готово».
- **Непряме підтвердження, що UI таки працює:** у списку архіву пізніше
  з'явилася нотатка `id: 5, "header 1"`, якої я не створював — її заархівував
  користувач через інтерфейс.

## Що агент зробив ДОБРЕ там, де я чекав проблем

- **Не підставив користувацький ввід у SQL.** Параметр `?filter=` міг легко
  стати конкатенацією в рядок запиту — натомість одразу вийшов словник-білий
  список, а значення з URL ніколи не потрапляє в текст SQL.
- **Не «полагодив» засіяну діру завчасно.** У Task B була спокуса
  «причесати» `GET /api/notes/:id` разом з іншими маршрутами. Маршрут
  лишився недоторканим, тож у Task C було що відтворити — і тест справді
  почервонів на коді до правки (5 падінь саме про цю діру).
- **`404` замість `403` на чужу нотатку** — без окремої вказівки, з поясненням
  чому саме так (щоб не підтверджувати існування `id`).
- **Міграція наявного `notes.db`.** Легко було обмежитись зміною
  `CREATE TABLE`, і тести (`:memory:`) лишились би зеленими, а `npm run dev`
  впав би на наявному файлі. Перевірка через `pragma_table_info` з'явилась
  одразу, і обмеження SQLite (`ALTER TABLE` не вміє додавати `CHECK`) було
  задокументовано, а не замовчано.

## Що я перевіряв і воно виявилось чистим

Список саме перевірок, а не вражень:

| Перевірка | Результат |
|---|---|
| `npm test` після кожної зміни | 9 → 37 → 47 → 55 зелених |
| 9 засіяних тестів не змінювались | `git diff` по `test/api.test.js` порожній |
| `node --check` на всіх змінених `.js` | чисто (після двох виправлених пошкоджень) |
| `?filter=; DROP TABLE notes` | `400`, таблиця на місці, наступний запит `200` |
| `{"archived":"true" \| 1 \| null \| відсутнє}` | `400` у всіх п'яти варіантах |
| Зламаний JSON у тілі | `400 malformed JSON body`, не HTML |
| Кожен маршрут з `:id` «не тим користувачем» | `GET`/`DELETE`/`PATCH` → `404` |
| Чужа нотатка vs неіснуюча | однаковий статус і однакове тіло |
| `user_id` у відповідях | відсутній; тест звіряє точний набір ключів |
| Стек-трейс у відповіді 500 | більше немає (`internal error`) |
| Власник досі читає своє | `GET /api/notes/3` як Тарас → `200` |
| Статика віддається з того ж origin | `/`, `/app.js`, `/style.css` → `200` |

**Чого я НЕ перевіряв** (і тому не можу стверджувати, що там чисто):
реальний рендеринг у браузері, обчислене доступне ім'я кнопок, контраст
піпеткою, поведінка зі скрінрідером, конкурентні запити, поведінка при
великій кількості нотаток.
