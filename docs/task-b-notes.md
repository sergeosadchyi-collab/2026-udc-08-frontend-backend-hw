# Task B — зміна схеми та ендпоінт

Коротко: що саме зроблено в базі й на сервері для фічі «архівування нотатки».

## 1. Колонка в базі

Додано колонку `archived` до таблиці `notes` у `app/src/db.js`:

```sql
archived INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0, 1))
```

Рішення й чому саме так:

- **`INTEGER`, а не `BOOLEAN`** — у SQLite немає булевого типу; `0/1` — це
  канонічний спосіб. У булеве значення це перетворюється один раз, на межі
  HTTP (`toNote` у `app.js`), щоб решта коду не думала про представлення.
- **`NOT NULL DEFAULT 0`** — нотатка не може бути «невідомо, чи в архіві».
  Наявні рядки автоматично стають активними, що й очікується.
- **`CHECK (archived IN (0, 1))`** — база сама не дає записати `2` або `-1`,
  навіть якщо хтось обійде валідацію в застосунку.

## 2. Міграція наявної бази

Тести створюють базу в пам'яті (`:memory:`), тож для них достатньо
`CREATE TABLE`. Але `npm run dev` пише у файл `notes.db`, який уже існував
**без** цієї колонки — для нього `CREATE TABLE IF NOT EXISTS` нічого не робить.

У SQLite немає `ADD COLUMN IF NOT EXISTS`, тому форма таблиці перевіряється
явно:

```js
const hasArchived = db
  .prepare("SELECT COUNT(*) AS n FROM pragma_table_info('notes') WHERE name = 'archived'")
  .get().n > 0;
if (!hasArchived) {
  db.exec("ALTER TABLE notes ADD COLUMN archived INTEGER NOT NULL DEFAULT 0");
}
```

Міграція ідемпотентна: запускається при кожному старті, але змінює щось лише
один раз.

> **Відоме обмеження.** `ALTER TABLE ... ADD COLUMN` у SQLite не вміє додавати
> `CHECK`. Тому база, мігрована зі старого файлу, має колонку без цього
> обмеження, а створена з нуля — з ним. Валідація в застосунку однакова в
> обох випадках. Щоб вирівняти повністю, потрібна перебудова таблиці
> (`CREATE TABLE notes_new … ; INSERT … SELECT … ; DROP …; ALTER … RENAME`) —
> для навчального проєкту це надмірно, але в продакшені я б зробив саме так.

## 3. Ендпоінт

```
PATCH /api/notes/:id/archive
Body: { "archived": true | false }
```

- `PATCH`, бо це часткова зміна одного поля, а не заміна ресурсу.
- Окремий підресурс `/archive`, щоб не відкривати загальний `PATCH` на нотатку:
  вузький ендпоінт неможливо випадково використати для зміни `user_id`.
- Явне значення в тілі замість «перемкни» без параметра — інакше два
  паралельних кліки дають непередбачуваний результат.
- Повертає оновлену нотатку, тож клієнту не треба вгадувати новий стан.

Списковий ендпоінт отримав параметр `?filter=active|archived|all`
(за замовчуванням `active`).

## 4. Валідація на сервері

| Вхід | Відповідь |
|---|---|
| `{"archived": true}` | `200` + оновлена нотатка |
| `{"archived": "true"}`, `1`, `null`, поле відсутнє | `400 archived must be a boolean` |
| зламаний JSON | `400 malformed JSON body` (а не HTML-сторінка Express) |
| `?filter=щось-інше` | `400 filter must be active, archived or all` |
| чужа нотатка | `404 not found` |
| неіснуючий або нечисловий `id` | `404 not found` |
| без заголовка `x-user-id` | `401 not authenticated` |

Свідомі рішення:

- **Ніякого приведення типів.** `"true"` — це помилка клієнта, а не привід
  здогадуватись. Мовчазне приведення ховає баги.
- **`filter` береться зі словника-білого списку**, а не підставляється в SQL.
  Значення користувача ніколи не потрапляє в текст запиту; є тест, який це
  фіксує.
- **Чужа нотатка — `404`, а не `403`.** `403` підтвердив би, що такий `id`
  існує.
- **Довжина `title` і `body` перевіряється на сервері** (200 / 10 000
  символів). `required` і `maxlength` у формі — підказка для користувача,
  а не захист: клієнта контролює користувач.

## 5. Зайві поля у відповіді

Усі хендлери вибирають один і той самий набір колонок:

```js
const NOTE_FIELDS = "id, title, body, archived, created_at";
```

`user_id` не віддається: викликач і так знає, хто він, а колонка, яка потрібна
лише для перевірки прав, не має бути у відповіді. Оскільки список один,
колонка, додана до таблиці пізніше, не «протече» за замовчуванням. Є тест, який
звіряє точний набір ключів.

> **Виняток, залишений свідомо:** `GET /api/notes/:id` досі повертає `user_id`
> і шукає нотатку лише `WHERE id = ?`. Це засіяна діра в авторизації — вона
> належить до Task C.
